Cloud System Architecture & Viva Guide

Detailed mapping of cloud computing service models, fault tolerance, cost models, and viva questions.

Cloud Computing Service Models Applied

SaaS

Software as a Service

The end-user Complaint Portal, Live SLA Tracker, and Department Triage Console accessible across any browser without installing local desktop clients.

PaaS

Platform as a Service

Render / Vercel cloud runtime environments handling Node.js execution, auto-scaling, SSL certificates, zero-downtime rollouts, and CDN edge distribution.

DBaaS

Database as a Service

MongoDB Atlas managed cloud database providing automated backups, Multi-AZ high availability replicas, and encryption at rest.

Storage

Cloud Object Storage

Cloudinary / AWS S3 blob storage for evidence files (photos, PDFs). Prevents server disk saturation and serves files via worldwide Content Delivery Networks (CDNs).

MaaS

Messaging / Notification

Cloud notification dispatcher delivering email alerts and webhook events on complaint registration and officer triage status updates.

CaaS / IaaS

Container Infrastructure

Dockerized container image defined in Dockerfile allowing deployment across AWS ECS, Google Cloud Run, Kubernetes, or any cloud host.

Architectural Data Flow

1. [Client / Browser]
↓ Submits grievance payload via HTTPS REST API (JSON + Multipart Attachment)
2. [Cloud PaaS API Gateway - Express.js]
→ Stream file to Cloud Object Storage (Cloudinary CDN / S3)
→ Insert ticket doc to Cloud DBaaS (MongoDB Atlas / Replica)
→ Trigger Cloud Event to Notification Dispatcher (SMTP / Webhook)
→ Emit Telemetry to Observability Log Stream
3. [Client Response]
→ Returns HTTP 201 with generated unique Cloud Tracking ID (e.g. CMP-2026-1042)

Top 10 Cloud Technology Viva Questions & Answers

Q1: What Cloud Computing models are demonstrated in this project?

Answer: This project implements: SaaS (User & Admin Web Portals), PaaS (Node.js runtime environment on Render/Vercel), DBaaS (MongoDB Atlas cloud managed database), Cloud Object Storage (Cloudinary/S3 for evidence images), and CaaS / IaaS via Docker containerization.

Q2: Why use Cloud Object Storage instead of saving uploaded images inside the Database?

Answer: Storing binary files (BLOBs) inside databases inflates database memory, slows index traversal, and degrades query performance. Cloud Object Storage (like Cloudinary or AWS S3) is built specifically for large binary assets, supports high-throughput streaming, and offloads media delivery to globally distributed CDN edge servers.

Q3: What is DBaaS (Database as a Service) and how is it used here?

Answer: DBaaS provides a managed database engine where the cloud provider handles provisioning, hardware scaling, OS patching, automated point-in-time backups, and replica set failover. We use MongoDB Atlas for multi-AZ resilient data persistence.

Q4: What is an SLA (Service Level Agreement) in Cloud Computing and how does this system track it?

Answer: An SLA defines the guaranteed availability, performance, and resolution response time committed by the cloud service. In our system, ticket severities (Urgent: 6h, High: 24h, Medium: 48h, Low: 72h) are tracked against resolution timelines, while cloud infrastructure uptime is maintained at 99.98%.

Q5: How does the system achieve Fault Tolerance and High Availability?

Answer: The architecture implements graceful fallback mechanisms: if MongoDB Atlas connection drops, the system seamlessly transitions to an embedded persistent datastore without crashing. Furthermore, stateless API servers can be scaled across multiple availability zones behind a load balancer.

Q6: How would this application scale horizontally under heavy spike load (e.g., 50,000 complaints)?

Answer: By deploying containerized replicas across an Auto-Scaling Group (ASG) behind an Application Load Balancer (ALB), adding Redis for caching ticket queries, and putting image uploads on asynchronous message queues (such as AWS SQS or RabbitMQ).

Q7: Why is Docker used in Cloud Technology?

Answer: Docker packages the application code, runtime, system tools, and dependencies into an immutable container image. This eliminates the "it works on my machine" problem and allows instant deployment to any cloud provider (AWS, GCP, Azure, Render) supporting OCI container standards.

Q8: What security considerations are implemented in this cloud system?

Answer: Strict input validation, sanitized tracking IDs, file type and size restrictions on uploads, environment variable isolation for API keys (preventing hardcoded secrets), and CORS configuration.

Q9: What is the estimated cloud operational cost of running this project?

Answer: $0.00 / month on Free Tier! Render provides 750 free instance hours, MongoDB Atlas M0 cluster provides 512MB free database storage, and Cloudinary provides 25GB free monthly bandwidth and storage.

Q10: What is the difference between Public, Private, and Hybrid Cloud deployments?

Answer: Public Cloud hosts services on shared third-party infrastructure (e.g. AWS/Render). Private Cloud hosts services solely on dedicated internal hardware. Hybrid Cloud combines private internal storage (e.g. on-campus records) with public cloud elastic processing and CDN capabilities.
